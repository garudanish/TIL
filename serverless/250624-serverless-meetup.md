## 서버리스 2부

> 현업에서 서버리스 구조를 운영하면서 겪었던 일을 통해, 서버리스 구조의 관리 지점들과 서버리스 구조를 관리하기 위한 노력들

### 서버를 관리한다는 것은?

- 초기 설정 및 구성
  - 인스턴스 유형 선택, OS 설치, 네트워크 구성, 소프트웨어 설치
- 업데이트
  - 보안 패치 등
- 재해 복구
  - 데이터 백업, 다중 AZ
- 모니터링
  - 로그, 메트릭, 성능 측정 등

#### 서버리스란?

> 개발자가 서버를 관리할 필요 없이 애플리케이션을 빌드하고 실행할 수 있도록 하는 클라우드 네이티브 모델

- OS, 소프트웨어 설치 없음, 업데이트 자동
- 데이터 백업, 자동 확장, 부하 분산 자동
- 로그, 메트릭 수집 자동!
  => 그래서 서버리스는 "서버를 관리할 필요가 없다"!
  물론, 다른 종류의 관심이 필요하다

#### 서버리스의 특징

- 설치 불필요, 사용량 기반 과금, 이벤트 기반 ㅗㅇ작, 기능의 추상화, 서비스 할당량, 높은 가용성, 자동 확장

### 서버리스에서 관리한다는 것은?

#### 서비스 할당량

- 구조 설계 시 서버리스를 채택한다면 서비스 요구 성능과 AWS 서비스 할당량(Quota)을 비교해봐야 한다.
- 서비스 할당량: 계정 혹은 리전에서 사용할 수 있는 자원과 성능의 최대치. 안정성과 가용성을 보장하기 위해 제한되어있음.
- 조정 가능한 것과, 조정 불가능한 것이 있음.
  - 서비스 요구 성능이 조정 불가능한 quota를 넘어선다면, 서버리스를 사용해선 안됨.

#### 실무 사례 1 - AWS Data Firehose

- API 요청 로그를 Data Firehose를 사용해서 S3에 적재. 후에 Athena + Glue로 데이터 분석할 계획이었음.
- 그런데 초당 PUT 요청 수, 레코드 수, 데이터 크기가 생각보다 처리량이 낮은데, 상향 조정이 불가능했음.
- 그래서 Firehose 여러개를 클러스터화 했음. 랜덤으로 Firehose를 선정해서 PUT 요청을 했음.
  - 대신 S3에 로그 파일이 작아지는 문제가 있었음.
  - Firehose를 늘린다고 해서 비용이 늘진 않았음. 데이터 처리량에 기반해 과금하기 때문.

#### 실무 사례 2 - AWS IOT Core

- 채팅 작성하면 채팅방 유저에게 메시지 전파. API 서버로 채팅 내용을 전달하면 서버는 IoT Core MQTT로 메시지 전달하려고 했음.
- 초당 아웃바운드 Quota가 Limit을 치면서 장애 발생
  - 인기 남돌 독점 영상이 공개 됐는데, 1만명이 동시 시청하면서 채팅하면서 초당 아웃바운드 게시 초과.
- 서비스 할당량 상향 요청, 메시지 큐에 모아서 전달, 너무 많으면 메시지 버림
- 주요 서비스 할당량을 모니터링하면서, 적절한 시점에 상향 요청해야 함

### 서버리스 아키텍처

> "거의 대부분의 서비스 요구사항은 서버리스로 해결할 수 있음"

- 하지만! 현실에는 돈, 시간, 조직 등 다양한 자원의 제한이 있음.
  - 따라서 시스템의 요구사항과 자원의 한계를 인지하고 적절한 트레이드오프가 필요함.
- Lambda + RDS 구조를 가정: 하이브리드 아키텍처 (서버리스 + 비 서버리스)
  - RDS를 100 req/sec 성능으로 가정하자. Lambda는 101 req/sec로 요청이 들어와도 다 받아줌. 결국 요청이 계속 밀리게 되고, 타임아웃이 나면서 장애가 발생할 것.
  - 서버리스는 약속된 할당량 안에서는 유용하고 빠르게 확장. 비 서버리스는 그것이 불가능(확장되는 데 시간이 오래 걸림)
- 1시간 진행하는 투표 중 첫 20분에 참여자의 80%가 참여. Spike Traffic!
  - 투표 전 비-서버리스를 수동으로 확장함. Scale out/up
- 파이널 실시간 생방송 투표에서 장애가 남;
  - 성능 확장 작업 / 시스템 점검을 했는데도 장애가 남
  - 3개월 간 지속적 트래픽으로 kafka 디스크 욜양이 100%에 가까워짐
  - 투표 시작 10분 후 디스크 용량 100% 도달.
  - Kafka 이벤트 발행 실패
  - 타임아웃이 길어지면서 API 응답 시간 증가 - 유저들은 새로고침 계속하며 부하 증가
  - Lambda 동시 실행 수 터지고, 서비스 전체 장애.
  - Kafka 디스크 용량 늘려 해결

### 비용

- 서버리스 비용은 예측하기 어려움.
  - 호출 횟수, 동작 시간, 처리 용량 등 사용량 기반이기 때문.
- 람다는 실행 시간이 짧고 예측이 어려운 작업에 유리함.
  - 서버리스에 불리한 작업은 EC2나 Pod을 고려할 것.
  - 이미지 매치 람다가 오래 걸렸을 것 같은데, 실행시간이 대략 어느 정도였나요?
- CloudWatch는 로그 저장 비용보다 수집 비용이 더 비쌈.
  - 로그 저장 기간 설정 필수.
  - 트래픽이 증가하면 로그 수집 비용 같이 증가.
  - 불필요한 로그, SQL 로그 등을 제거하면 비용 절감 가능
- CloudFront
  - 이미지 캐싱 시 Lambda@Edge로 리사이징 + WebP 변환 필수.
  - 이미지를 1MB -> 100KB로 축소하면 10배 절감 효과 있음.
  - 이거 튜닝하고 싶다.
